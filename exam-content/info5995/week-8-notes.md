## 1. Important points from slides

### 1a. Software security (slides 2–7 of the first block)
- **Definition [S]:** security is an *engineering property across the complete software lifecycle*. Design, develop, test and maintain software so it resists attack and protects users' data. Sub-title: "Designing systems that remain trustworthy under attack."
- **CIA [S]:** Confidentiality = prevent unauthorised *disclosure*; Integrity = prevent unauthorised *change*; Availability = sustain *dependable access*.
- **Security mindset [S]:** prevent vulnerabilities *before* deployment — and continue protecting the system *after* deployment. "Connection to Week 1: security lifecycle → how we secure software across that lifecycle."
- **Case studies [S] (slide "Why Does Software Security Matter?", sources FTC; CISA CVE-2021-44228; Progress CVE-2023-34362):**

| Year | Incident | Vulnerability | Impact |
|------|----------|---------------|--------|
| 2017 | Equifax | Unpatched component | ~147 million people |
| 2021 | Log4Shell | Vulnerable library | Remote code execution |
| 2023 | MOVEit | SQL injection | Mass data theft |

  Bold line: "Many major breaches exploit software vulnerabilities rather than breaking cryptography." Common thread: *a software weakness, configuration issue, or dependency gave the attacker a way in.* (Slide phrase "Small implementation weaknesses can produce population-scale consequences.")
- **Where vulnerabilities come from [S]:** six lifecycle stages, each with a typical defect: 01 Requirements → *abuse case omitted*; 02 Design → *trust boundary missed*; 03 Implementation → *unsafe data handling* (highlighted); 04 Testing → *adversarial path skipped*; 05 Deployment → *insecure default*; 06 Maintenance → *patch delayed*. "A vulnerability can be introduced — or removed — at every lifecycle stage." "The later a defect is discovered, the more architecture, data and operations may already depend on it."
- **Common vulnerabilities [S] (several reflected in OWASP Top 10, 2021), one-liners:**
  - SQL Injection — *data becomes a database command*
  - Cross-Site Scripting — *content becomes browser code*
  - Broken Access Control — *identity is mistaken for authority*
  - Security Misconfiguration — *unsafe capability is exposed*
  - Vulnerable Components — *inherited supply-chain risk*
  - **Shared root cause:** the system trusts data, identity, configuration or dependencies more than it should.
- **Defence in depth [S]** — six layers left→right, build time → run time; "Layered controls stop one missed defect from becoming a successful attack":
  1. Secure Coding = **PREVENT**
  2. Testing = **CHALLENGE**
  3. Static Analysis = **INSPECT**
  4. Dynamic Analysis = **PROBE**
  5. Monitoring = **OBSERVE**
  6. IDS / IPS = **DETECT / BLOCK** (highlighted; run time)
  "These layers work together across the software and system security lifecycle." (Slide gives only the one-word role for static/dynamic analysis; no SAST/DAST acronyms anywhere in the deck.)
- **Lecture roadmap [S]:** 1 Software Security → 2 Database Security → 3 SQL Injection → 4 Injection Prevention → 5 Inference Attacks → 6 XSS → 7 XSS Prevention → 8 IDS/IPS. Guiding question: "Where should we place the next control to reduce risk most effectively?"

### 1b. Database security
- **What is a database [S]:** "a managed system for storing, relating, querying and updating persistent data." **Relational** = tables, rows, columns and constraints (PostgreSQL, MySQL). **Non-relational** = documents, key-value, graph or wide-column (MongoDB, Redis, Neo4j). "A database is more than files: it enforces structure, relationships, transactions, concurrency and controlled access to shared state." Security implication: compromise affects not only stored records but every application and decision that depends on them.
- **Why valuable targets [S]:** "crown-jewel data": personal data (identity, contact, behavioural), financial data (payments, transactions, account history), credentials (passwords, tokens, access secrets), intellectual property (research, source data, commercial knowledge). "One successful query can extract thousands or millions of records."
- **Database security goals — CIA at the data layer [S]:**

| Goal | Meaning | Controls (as on slide) |
|------|---------|------------------------|
| Confidentiality | Only authorised subjects can view *specific* data | authentication, least privilege, encryption, masking |
| Integrity | Data remains accurate, valid and traceable | constraints, transactions, validation, audit logs |
| Availability | Authorised workloads can access data when required | replication, backup, recovery, capacity and DoS resistance |

  Objective: "controlled, correct and dependable use of data — not merely keeping attackers outside."
- **Goals → threats [S]:** two ways the guarantees fail: **1 SQL injection = DIRECT** ("manipulates a database query through unsafe application input handling") and **2 database inference attacks = INDIRECT** ("reveal sensitive information indirectly through legitimate queries").

### 1c. SQL injection
- **Definition [S]:** malicious input changes the SQL query executed by an application. **Key message: "Attackers exploit insecure application code — not the database itself."** Succeeds when user-controlled text is interpreted as SQL syntax.
- **Worked example [S] (4-step flow):** 1 normal input `Username: Alice` → 2 malicious input `Alice' OR '1'='1` → 3 executed query `SELECT * FROM users WHERE username='Alice' OR '1'='1';` → 4 result: **authentication bypass, unauthorised data access.** "User input becomes part of the SQL command, changing its intended behaviour." (`'1'='1'` is always true, so the WHERE clause matches every row.)
- **Prevention [S]:** core defence is *structural — keep data separate from executable SQL.*
  - ✓ **Prepared statement** — "SQL structure is fixed before user data is supplied": `cursor.execute("SELECT * FROM users WHERE username=?", (username,))` (the `?` placeholder; the value is passed separately).
  - ✕ **String concatenation** — "input is merged into the command and may become syntax": `"SELECT * FROM users WHERE username='" + username + "'"`.
  - Three supporting controls: **input validation** (constrain accepted formats), **least privilege** (limit database permissions), **ORM frameworks** (use safe query APIs *correctly*).
  - Tagline: "Separate user input from SQL commands."
- **Input validation and sanitisation table [S]** ("accept only data that matches the field's expected type, range and syntax"):

| Input | Validation rule | Safe handling |
|-------|-----------------|---------------|
| Username | Letters and numbers only | Reject characters outside the allowlist |
| Age | Integer from 0 to 120 | Parse as a number; enforce range |
| Email | Valid email structure | Use a trusted email validator |
| Comments | Text, not executable markup | Encode HTML output; sanitise if HTML is allowed |

  Banner: "Never trust user input. Validate input before processing and encode before output."
- **[X] extra resources on SQLi:** "Prepared statements separate SQL structure from user-supplied values and are **the primary defence**." Reading focus: parameterised queries, safely implemented stored procedures, **allow-list validation for identifiers**, **why escaping alone is fragile**; "least-privilege database accounts"; "why dynamic string construction is dangerous". Practical connection: *"Building a login form? Use parameterised queries; **validation is useful but does not replace query parameterisation**."* Self-check Q1: "Why do parameterised queries prevent SQL injection more reliably than input filtering?" Self-check Q5: "How does least privilege reduce the impact of a successful injection attack?"

### 1d. Database inference attacks
- **Core idea [S]:** "The attacker does not bypass access control — they learn from what the system reveals." Example: allowed query `SELECT * FROM users WHERE username='alice' AND salary > 100000;` — no salary value is returned, but *result found = True / no result = False* lets the attacker **infer Alice earns more than $100,000**. "A sequence of low-information answers can reveal a high-value secret."
- **In practice [S]:** "Real systems leak through combinations of legitimate views, counts, timings and metadata." Conference-review setup: (1) reviewers are anonymised; (2) authors must not see discussion of their own submission; (3) reviewer identities are visible only to co-reviewers of the same paper. **Leakage surface:** progress lines → behavioural pattern; review counts → paper-level metadata; names on charts → identity signal. "Individually harmless signals become identifying when combined." "**Inference risk grows as the anonymity set becomes smaller.**"
- **Procrastination chart [S]:** x-axis = days before deadline; y-axis = fraction of work complete (0 to 1.0); **blue lines = individual progress, red = average progress**; pattern = little progress early, sharp rush near the deadline. "A useful aggregate visual can become a privacy leak when individual identities remain attached."
- **Linkage attack [S]:** three ingredients — (1) named progress lines (identity), (2) review counts per paper (assignment clue), (3) distinct progress patterns (behavioural fingerprint). **Linkage attack = match reviewer behaviour to paper review counts → infer who reviewed which paper.** "Small anonymity sets make inference easier and automation more accurate."
- **[X] concept map:** inference-attack connection = "query controls, aggregation and larger anonymity sets". Practical connection: "Consider what can be learned by combining legitimate answers, counts, timings and metadata." Self-check Q2: "How does a database inference attack reveal information without directly returning the secret?"

### 1e. XSS
- **How it works [S]:** "The vulnerable site delivers attacker-controlled JavaScript to a trusted user's browser." 3 steps: (1) attacker injects script into the **trusted website, which stores or reflects untrusted content**; (2) the page + script is delivered to the victim user; (3) session data / actions are sent back to the attacker. **"The browser trusts the website, not the attacker. If the website serves malicious code, the browser executes it anyway."**
- **One input, two outcomes [S]:** comment field input `<script>alert("INFO5995")</script>` — the app stores or reflects it; browser shows an alert "This page says INFO5995" = JavaScript executed. **"If output is not encoded, data becomes code."**
- **Why dangerous [S]:** code executes in the security context of the trusted website: (1) session theft (steal tokens/impersonate users); (2) unauthorised actions (submit requests as the victim); (3) phishing (replace trusted content with deceptive UI); (4) data exfiltration (read and transmit accessible page data). **"XSS does not 'hack the browser.' It abuses the browser's trust in a vulnerable application."**
- **Preventing XSS [S]:** (1) **Encode output** — convert `<`, `>`, `&`, quotes and other characters to safe equivalents (highlighted as the primary one); (2) **Sanitise allowed HTML** — use a proven library when rich text is genuinely required; (3) **Use safe frameworks** — prefer auto-escaping templates, avoid unsafe DOM APIs; (4) **Add browser safeguards** — Content Security Policy (CSP) as an additional layer. Banner: **"Validate input. Encode output. Keep data separate from code."**
- **[X] on XSS:** types — **reflected, stored, DOM-based** (the deck never defines them; the extra PDF only names them in reading focus + self-check Q3 "What is the difference between reflected, stored and DOM-based XSS?"); "why output context matters" (HTML, attribute, JavaScript and URL contexts → self-check Q4 "Why must output encoding match the output context?"); "framework auto-escaping and escape hatches"; "HTML sanitisation"; "CSP as defence in depth". Practical connection: *"Displaying user-generated content? Encode output for its exact HTML context and sanitise only when rich HTML is genuinely required."* Concept map: XSS = "untrusted content executes in a user's browser" → "context-aware output encoding and sanitisation".
- Reflected vs stored vs DOM (standard definitions, **not on the slides — outside knowledge, flag if used**): reflected = payload comes from the current request (e.g. URL parameter) and is echoed back; stored = payload saved by the server (comment, profile) and served to later visitors; DOM-based = client-side JS writes untrusted data into the page without the server reflecting it.

### 1f. System security
- **Why system security [S]:** "Deployment changes the problem: the system is now reachable, observable and continuously attacked." Threats: (1) **brute-force** — repeated login attempts; (2) **malware** — malicious code and ransomware; (3) **scanning** — discovery of exposed services; (4) **denial of service** — resource exhaustion; (5, running-system box) *insider misuse — abuse of legitimate access* [it appears in the text extraction as a fifth tile]; "attack surface changes with users, traffic, configuration and time." **"Prevention is not enough — systems must also detect and respond."**
- **Software vs system security [S]:**

| | SOFTWARE SECURITY | SYSTEM SECURITY |
|---|---|---|
| Focus | Build secure software | Protect deployed systems |
| Objective | Prevent vulnerabilities | Detect and respond to attacks |
| When | Development and testing | Operation and maintenance |
| Examples | SQL injection, XSS | IDS, IPS |

  Timeline: before deployment (software) | DEPLOYMENT | after deployment (system). "Software security reduces weaknesses before deployment; system security detects and responds after deployment. **Both are essential.**" [X]: "Neither replaces the other."
- **IDS [S]:** "observes host or network activity and alerts on suspicious behaviour." **Where it watches:** **HIDS** = one computer or server; **NIDS** = traffic across a network segment. **How it detects:** **signature-based** = known attack patterns; **anomaly-based** = deviation from normal behaviour. **Common tools:** Snort, Suricata, Zeek. **"IDS detects and alerts — it does not automatically stop the attack."**
- **IPS [S]:** "observes traffic like an IDS, but **sits inline** and can automatically intervene." Loop: **INSPECT → DECIDE → ACT**, inline with traffic between attacker and protected system. Actions: **block malicious traffic, drop suspicious packets, reset connections, quarantine hosts.** "IPS detects and prevents attacks in real time."
- **IDS vs IPS table [S]:**

| Feature | IDS | IPS |
|---------|-----|-----|
| Purpose | Detect attacks | Detect and block |
| Action | Generate alerts | Automatically intervene |
| Deployment | Monitoring path | Inline with traffic |
| Response | Passive | Active |

  **IDS = security camera** ("sees the intruder and raises the alarm"); **IPS = security guard** ("sees the intruder and blocks the door").
- **Brute-force scenario [S]:** attacker → thousands of attempts → web server. IDS: detects failures, alerts the team. IPS: blocks source IP, logs the incident (admin/security team). Discuss: "Would an IDS alone stop this attack? Why or why not?"
- **Key takeaways [S]:** Software security = Prevent (design, develop, test securely) / Protect data (databases concentrate sensitive info) / Understand attacks (SQLi, inference, XSS) / Build safely (parameters, validation, encoding, least privilege). System security = Assume exposure (risk continues after deployment) / Observe (monitor hosts, networks, behaviour) / Detect (IDS identifies suspicious activity and alerts) / Respond (IPS blocks or mitigates in real time). Lifecycle strip: design → build → test (software) | deploy → monitor → respond (system). **"Security is continuous: secure software + secure systems + continuous monitoring."**
- **[X] practical connections (extra PDF only, not in the slides):**
  - "Protecting a database? Apply least privilege, **protect backups and logs**, and monitor unusual query or access patterns."
  - "Deploying an IDS? **Tune signatures and baselines so useful alerts are not buried in false positives.**"
  - "Deploying an IPS? **Plan safe fail-open/fail-closed behaviour** and **test blocking rules before production use**." Self-check Q10: "What operational risks can an incorrectly tuned IPS introduce?" (Standard answer, outside the deck: false positives block legitimate users/traffic; fail-closed can cause outage if the IPS fails, fail-open lets attacks through.)
  - NIST SP 800-94: HIDS/NIDS deployment models (also application-focused monitoring), signature vs anomaly, passive alerts vs inline blocking, tuning/monitoring/maintenance. Self-check Q9: "Why must an IPS be deployed inline to block traffic?" Q8: "Why does an IDS generate alerts without necessarily stopping an attack?" Q7: "How do HIDS and NIDS differ in their observation points?" Q11: "How do software security and system security complement one another?"

### Software / programming asides (lecturer's words; these are the items behind user-summary items 1–2)
- "Software security: designing systems that remain trustworthy under attack." What is software? Any **application** running on a platform; the OS is *system software*; firmware also (student). Today = application software.
- **Software development life cycle**: requirements → design (on paper) → implementation (code) → testing/deployment. Stages are **not isolated** (iterate back; while developing you already consider deployment/testing/security — he calls this "DevOps"). Security must be considered at *every* layer or you leave loopholes.
- **Attack surface depends on the software:** a program that asks for **no user input cannot suffer SQL injection** (no parameter to inject into). "You decide the attack surface, then secure it."
- **Implementation-phase example — divide by zero:** he said the result is "infinity"/**it crashes**; general rule: "in any CPU architecture, if you try to access something that doesn't exist, your application crashes"; stack overflow = a crash because the stack is full and you access an address outside it. Later fixing beats propagating: "the earlier you fix the problem, the better; if it propagates it gets bigger. That's the crux of software security."
- **Garbage value:** declaring an array does **not** give an empty one — it "genuinely" holds **garbage values**, which is why you **initialise it to zero**; the same garbage may appear on repeated runs but is **random and can't be relied on**; some architectures return random/garbage when you do something prohibited.
- **Three disciplines of programming:** (1) how to program; (2) *efficient* programming (data structures); (3) **secure coding** — a separate subject: "security-aware coding". Secure coding is usually taught in **C/C++** (not Python — too high-level, less control) because of **pointers and manual memory**.
- **Pointers:** "I allocated memory but forgot to deallocate it — hanging pointer"; if you don't free memory and destroy pointers "your program can become really insecure". If an attacker reaches your software (e.g. via XSS "or something else") and can control a leftover pointer, "they can play with your memory / add anything to it" — corrupting memory is critical. Goal of secure coding: write so the program is **naturally secure** with no loopholes to crash or compromise. Even without doing secure coding you must be aware of your pointers. (He explicitly stopped short of the detail: "let's not discuss it further"; **SAFE-free/NULL-after-free/RAII/smart pointers were NOT mentioned.**)
- **Static vs dynamic analysis vs monitoring (verbal version of the defence-in-depth slide):** *static analysis* — "I have access to your **code** and analyse how secure it is"; *dynamic analysis* — "I give you access to my **software, not the code**; test it **while running**; **penetration testing**"; *monitoring* — software is up and running; continuously observe whether things are under control and whether someone is trying to break in. Then "that's defence in depth." **SAST/DAST acronyms not used.**

### Database asides
- A database is **not only storage** — it preserves **relationships between data**; tables are linked by **foreign key constraints** ("if you miss the connection, you miss information"). His toy example: a weather table and an attendance table linked by a relation.
- Why databases matter: CommBank (financial), Facebook (social), Medicare (health), university (education) — and the **chat/AI providers** (ChatGPT/OpenAI/Grok/Claude "know you better than anyone") — "the data on these websites is very, very important."
- **CIA at the DB layer — his versions:** *Confidentiality* — store data **encrypted**, apply **least privilege** and **authentication** (no one sees data unless they authenticate). *Integrity* — because real databases are big with many tables, **the same fact can be derived from two different sources; check they stay consistent** (his example: classroom capacity table vs enrolments table vs which-lecture-in-which-room table; enrolments must stay ≤ room capacity). *Availability* — **create backups and keep them in a different network** so corrupted data can be recovered (photo-copies analogy).
- Two database threats named verbally: **SQL injection** and **inference attack**.

### SQL injection (verbal walkthrough)
- Login flow: system runs `select * from users where username = <input> and password = <input>`; if a row matches you get in. Attacker who doesn't know the password types a password plus `or 1=1`; the condition becomes "match the password **or** 1 equals 1" and 1=1 is always true → access without knowing the password. Restated: "through input fields I'm sending you **code**; if it executes against your database, that's SQL injection." He said "Attackers trick the database" (student's answer) then reframed as *input becomes part of the query*. "If one equals to one doesn't work, hackers try hundreds of other always-true tricks" — blocking must be systematic, not pattern-by-pattern; ~90% of a 33-feature portal touches the database.
- **Defences he gave ("four ways… I don't remember the fourth; three are enough"):** (1) **input validation** — value must be within a defined range/type (expect a number, reject a string; block silently); (2) **input sanitisation** — "you sanitise your hands: remove the viruses" — strip characters like `%`, `/`, `<`, `>` that could turn input into a command; (3) **parameterised queries** — `... where user_id = ?`: input **never becomes part of the query, only the value of a variable inside it**; even `ABC123 or 1=1` is treated as a (wrong) password string, so it fails. He labelled parameterised queries the "third step, which is very important." He ends with: "you do two things, sanitisation and validation, and on top of that you can do parameterised queries."
- Slide walkthrough: "username letters/numbers only" → **validation**; "reject characters outside the allow-list" → he called this **sanitisation** (remove/block %, etc.); "email — valid structure, must contain '@', use a trusted email validator."

### Inference (verbal)
- Everyday analogy: after an exam you **infer** how a friend did from how confident they look; "you don't have direct access to the information but can infer what is going on."
- `salary > 100000` query returning true/false → attacker infers Alice earns more/less than 100 k (he: "this Alice earns more than me").
- **Error messages are an inference channel [V, not on slides]:** a verbose error ("value of this variable couldn't be assigned because… range must be…") reveals variable names, structure and allowed ranges; the attacker provokes more errors, learns more, then attacks. **"Don't be an information provider"** — return a bland "access blocked". Hackers are "information seekers".
- Conference analogy: single-blind vs double-blind review; a reviewer friend can guess the author from the *topic* even without names; and from **progress footprint** ("Part is the last-minute doer — huge progress in the last two files, must be Part") — behaviour and topic can reveal identity.
- "Do you understand how inference can lead to many other attacks?" — yes; inference feeds later attacks.

### XSS (verbal)

- XSS = "similar to SQL injection, but your input becomes **PHP / JavaScript / Python code** (script)"; "usually from a third party / remote machine — that's why it's called cross-site"; injects code into "any page of the website through input fields and you will not be able to block it [without controls]". Demo slide: `INFO5995` typed in a box appears inside an `alert(...)`; instead of that text you could input a whole script. Consequences he named: get **session tokens**, do **unauthorised actions**, **steal data / send it elsewhere**.

- **XSS prevention — his version ("three methods"):** input validation (length limits; expected string vs number) and **input sanitisation** (delete angle brackets `<`,`>`, ampersand, quotes — characters that can become commands). Languages named: HTML, JavaScript, XML, PHP. **XSS is less common in Android apps** (logic is Java/Kotlin) "but the front end is still XML-based".

### System security (verbal)
- Software security = one application; **system security = the whole operating system / all apps / whatever package arrives / the whole network**; you block malicious content; tools = **firewall, IDS, IPS** (and antivirus). "To protect a system we have IDS, IPS and firewalls; to protect *software* we avoid SQL injection, protect against XSS, inference attacks."
- **Risk-based protection:** "If you have honey, bees will come." Hackers don't waste time on a kid's computer (little payoff); they go for big fish (his example: attacking the university's Canvas for ransom). Do a **risk analysis**; don't deploy the whole infrastructure to protect a low-value machine — *but* a weak device connected to a prestigious network can become an **insider threat** to that network, so the network provider protects it (e.g. via **cloud services**; if you get attacked while connected you may be quickly isolated).
- **Air-gapped example:** a computer never connected to the internet does **not need a network firewall**; if you sometimes plug in **USB/other media** you may need **antivirus** to scan it. "It depends on the scenario — the likelihood decides how much protection you need."
- **Firewall vs antivirus [V — this is the only place firewall/antivirus appear; NOT on slides]:** a **firewall is a filter on traffic** — inbound and outbound; e.g. block packets from a given IP, block a protocol (block SMTP = no emails); rules you define; also blocks computers that match known attack rules. **Antivirus is a scanning tool** — scans the files on your system, quarantines malicious ones (delete later); **modern antivirus can be real-time** (keeps running and scans whatever comes new).
- **Firewall vs IDS [V]:** an *intrusion* = someone trying to intrude. He says firewall works on **set rules** (block on sight, like a social-media account auto-banned for using a certain word), whereas an IDS "looks at the **holistic pattern** over time" (like reviewing six months of posts), e.g. a peer that always used TCP/SMTP suddenly switches to ICMP — and he says modern IDS are "mostly AI-based". ## 6. Contradictions / places where the transcript, slides and the user's summary disagree (C1–C8)
